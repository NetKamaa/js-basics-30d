# Day 10 — Guards Drills

## 1. Добавление пустой задачи (пустая строка или пробелы)

**Некорректное действие:**  
Пользователь вводит пустую строку или только пробелы и нажимает `Add` / Enter.

**Где защищаться:**

- `handler` — `handleAdd`
- `action` — `addItem`

**Чем защищаться:**

- `error` — функция `getValidationError(text)` возвращает `"Введите текст"`.
- `guard` — ранний `return` в `handleAdd`, если есть ошибка.
- дополнительный `guard` в `addItem` — если после `trim()` строка пустая, вернуть прежний `state`.

---

## 2. Добавление слишком длинного текста (> 60 символов)

**Некорректное действие:**  
Пользователь вводит текст длиннее 60 символов и нажимает `Add`.

**Где защищаться:**

- `handler` — `handleAdd`

**Чем защищаться:**

- `error` — `getValidationError` возвращает сообщение о превышении длины.
- `guard` — если есть ошибка, сразу `return` и не вызывать `addItem`.
- `disabled` — кнопка `Add` отключена при наличии ошибки (`hasError` → `canAddItem`).

---

## 3. Попытка обойти disabled и принудительно вызвать добавление

**Некорректное действие:**  
Пользователь вручную снимает `disabled` через DevTools или программно вызывает клик.

**Где защищаться:**

- `handler` — `handleAdd`

**Чем защищаться:**

- `guard` — повторная проверка через `getValidationError` внутри handler.
- если ошибка есть — ранний `return`.

> UI (`disabled`) — это удобство.  
> Реальная защита — в handler.

---

## 4. Удаление элемента с некорректным id

**Некорректное действие:**

- кнопка вне `<li>`
- отсутствует `data-id`
- `data-id` не число

**Где защищаться:**

- `handler` — `handleListClick`

**Чем защищаться:**

- `guard`:
  - если `dataset.role !== "delete"` → `return`
  - если `!li` → `return`
  - если `!Number.isFinite(id)` → `return`

Ошибка пользователю не показывается — действие просто игнорируется.

---

## 5. Удаление несуществующего элемента (двойной клик / устаревший DOM)

**Некорректное действие:**  
Пользователь повторно удаляет уже удалённый элемент.

**Где защищаться:**

- `action` — `removeItem`

**Чем защищаться:**

- `guard` — проверить, существует ли элемент в `state`:
  - если нет → вернуть прежний `state`.

Ошибка не выводится — поведение остаётся безопасным и стабильным.

# Почему `throw` не нужен для ошибок валидации формы?

## 1. Это ожидаемое поведение пользователя

Пустой ввод, слишком длинный текст — это нормальные сценарии работы формы.  
`throw` используется для аварийных ситуаций, а не для обычных UX-ошибок.

---

## 2. Валидация — это часть логики UI

Функция `getValidationError` возвращает строку ошибки.  
Мы:

- показываем её пользователю
- блокируем действие
- даём возможность исправить ввод

Это контролируемый поток выполнения, без исключений.

---

## 3. Исключения — для неожиданных системных ошибок

`throw` уместен, когда:

- сломан `JSON.parse`
- повреждён `localStorage`
- пришли данные неправильной структуры
- произошёл сбой сети

Это ошибки разработчика или системы, а не пользователя.

---

## 4. Исключения усложнили бы код

Если бы валидация делала `throw`, пришлось бы:

- оборачивать каждый handler в `try/catch`
- ловить обычные ошибки ввода
- усложнять поток выполнения

Для формы это избыточно.

---

# Вывод

- Ошибки пользователя → `error + guard + disabled`
- Ошибки системы → `throw / try-catch`

Форма — это не место для исключений.  
Это место для контролируемой UX-логики.
